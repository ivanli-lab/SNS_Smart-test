# Changelog 撰寫規則

## 檔案命名規範

格式：`YYYYMMDD-功能名稱-v版號.md`

範例：
- `20260109-viewport-selector-v1.0.0.md`
- `20260109-button-detection-fix-v1.0.1.md`
- `20260110-test-refactor-v1.1.0.md`

命名規則：
- 日期：8 位數字，YYYYMMDD 格式
- 功能名稱：使用英文，單字間用連字號 `-` 分隔，簡短明確
- 版號：使用 `v` 前綴 + 語義化版本號

## 內容撰寫規範

### 基本原則

1. 只註記功能，不使用形容詞
2. 使用條列式，一行一個功能點
3. 使用動詞開頭（新增、修改、移除、修復）
4. 不描述技術細節，只說明功能變化

### 分類標籤

使用以下分類標籤：

- **新增 (Added)**：新功能
- **修改 (Changed)**：既有功能的變更
- **移除 (Removed)**：移除的功能
- **修復 (Fixed)**：錯誤修正
- **重構 (Refactored)**：程式碼重構（不影響功能）

### 範例格式

```markdown
# v1.0.0 (2026-01-09)

## 新增
- 解析度選擇功能
- 5 種裝置預設解析度

## 修改
- Playwright 瀏覽器開啟尺寸可自訂

## 修復
- All Streamers 排序按鈕檢測失敗
```

### 禁止使用的表達方式

❌ 不良範例：
- "大幅改善了測試速度" (有形容詞)
- "優化了按鈕檢測邏輯" (太抽象)
- "重構了 check.js，將 2077 行拆分為 12 個模組" (技術細節)

✅ 良好範例：
- "測試執行時間減少 30%"
- "按鈕檢測改用 ID 選擇器"
- "測試步驟模組化"

## 版本號規則

- **Major (x.0.0)**：不向後兼容的變更
  - 移除既有功能
  - API 介面變更
  
- **Minor (0.x.0)**：向後兼容的新功能
  - 新增測試項目
  - 新增配置選項
  
- **Patch (0.0.x)**：向後兼容的修復
  - 錯誤修正
  - 文檔更新

## 提交流程

1. 完成開發與測試
2. 更新 `public/config.js` 的 VERSION 變數
3. 在 `documents/changelog/` 創建新的 changelog 檔案
4. 執行 git commit，commit message 引用 changelog 檔案名稱
